# Post-v1.5 change audit

**Audit date:** 2026-08-23
**Baseline:** annotated tag `v1.5.0`, commit `1e8494803018847ba70de4c28b17d68104ba62db`
**Audited tip:** `68ebb2fa9010d235ce2bf4904220dbc8673d61e3` plus the tracked and untracked working tree present at audit start
**Mode:** audit only; no application, build, workflow, resource, or existing documentation file was changed
**Detailed evidence:** [2026-08-23-v1.5-delta-evidence.md](2026-08-23-v1.5-delta-evidence.md)

## Executive verdict

**Release readiness: HOLD.**

The post-v1.5 work is unusually large and contains strong engineering improvements: the old neural decoder and roughly 26 MB of model assets were removed, CTC and geometric swipe engines gained extensive real- and synthetic-corpus coverage, lint now gates new errors, privacy boundaries were tightened, TalkBack support was added, and the current automated JVM gates are green.

The release should nevertheless not be tagged yet. There are **7 P1 findings**:

1. Backup ZIP imports stream unbounded media and encrypted containers to disk, mutate live media before validation, and do not roll back files after failure.
2. The workflow named “Accessibility Tests” does not run an accessibility test, while the “Visual Regression” job performs no comparison.
3. A release tag bypasses the normal lint, security, and emulator workflows and publishes after JVM tests only.
4. The v1.6 release metadata contradicts both the code and itself.
5. Default CTC lost the former main-dictionary fuzzy rescue.
6. Default CTC silently ignores the configured secondary language on the swipe path.
7. CTC drops words whose Latin surface cannot be projected to `a-z`, including common German `ß` words.

No P0 issue was found. The P1 items are bounded and actionable; none requires an architectural reset.

Severity meanings used here:

## P1 findings — release blockers

### CK-150-001 — Backup archive imports can exhaust storage and corrupt live media before validation

**Area:** security, privacy, availability, data integrity
**Severity:** P1
**Introduced after v1.5:** yes; the full/encrypted backup and archive-abuse work is in this delta

#### Evidence

- `BackupRestoreManager.importClipboardHistoryZip` bounds only JSON and the number of entries. Media uses unbounded `zipIn.copyTo(out)` at `BackupRestoreManager.kt:1431-1441`.
- `importFullBackup` repeats the same unbounded copy at `:1882-1889`.
- `MAX_JSON_ENTRY_BYTES` and `MAX_IMPORT_ENTRIES` at `:2049-2062` do not bound per-media bytes, total decompressed bytes, or total files written.
- Encrypted ZIP input is decrypted without a ciphertext/plaintext byte ceiling to a cache file at `:255-270`; a valid or invalid giant container can fill cache storage before the GCM tag is checked.
- Media is written directly to the live `clipboard_media` location while the ZIP is still being parsed. Manifest presence is checked only after the stream is exhausted at `:1904-1906`.
- The failure paths delete only the decrypted cache file (`:1999-2020`). They do not remove newly created or partially overwritten media.
- `BackupRestoreArchiveLimitsTest` covers oversized JSON and entry count, but explicitly does not test media-byte or aggregate-byte limits.

The result is more than an out-of-memory concern. A malformed plaintext backup selected in the UI can create or overwrite media files, omit its manifest, fail, and leave those mutations behind. A compression bomb can consume the app/device storage. The encrypted headless route is harder to exploit by default because it requires the user’s passphrase, but it reaches the same unbounded substrate.

#### Required TODOs

- [ ] Parse and authenticate into an isolated staging area; do not write to live `clipboard_media` until the manifest and JSON are validated.
- [ ] Add a streaming `copyBounded` helper with both `MAX_MEDIA_ENTRY_BYTES` and `MAX_IMPORT_TOTAL_BYTES`. Do not trust `ZipEntry.size` as the enforcement mechanism.
- [ ] Add an encrypted-container/decrypted-temp maximum and fail before the cache partition is exhausted.
- [ ] Track every staged/created file and remove it on every exception; commit staged files only after the DB import succeeds.
- [ ] Avoid overwriting an existing live media file before validation. Use new staging names and an atomic move/merge policy.
- [ ] Reject duplicate manifest/JSON entries and require the full-backup manifest before accepting section/media entries, or perform a validation pass before an apply pass.
- [ ] Add tests for: one oversized media entry, many individually valid entries exceeding the total, encrypted oversized input, missing/late manifest, duplicate entries, partial write failure, and rollback preserving an existing media file.

#### Acceptance test

A highly compressible media entry larger than the per-entry cap, a ZIP larger than the aggregate cap, and a full backup without a valid manifest must all fail with no live DB or media-directory changes and no surviving staging file.

**Severity:** P1

#### Evidence

- `.github/workflows/ui-testing.yml:265-279` names the job “Run Accessibility Tests” and publishes an accessibility summary.

- The “Visual Regression” mode only opens Settings and captures a screenshot (`emulator-ci.sh:80-86`). It has no baseline, pixel/perceptual comparison, or assertion.

This is a false-green test signal for a headline v1.6 feature. The implementation may be good, but the workflow cannot establish that.

#### Required TODOs

- [ ] Run `tribixbite.cleverkeys.a11y.KeyboardAccessibilityInstrumentedTest` and parse the instrumentation verdict exactly as the curated gate does.
- [ ] Add at least one service-level TalkBack/touch-exploration smoke assertion; merely setting `accessibility_enabled=1` is not enough.
- [ ] Rename the visual job to “Screenshot capture” unless a checked-in/approved baseline and a failing comparison threshold are added.
- [ ] Make the workflow summary describe only assertions actually executed.
- [ ] Add a CI test that pins the curated class list or derives it from an explicit annotation/list so new critical instrumented classes cannot remain orphaned.

#### Acceptance test

Deliberately break a key content description and deliberately alter the reference screen. The accessibility and visual jobs must each fail for their corresponding regression.

### CK-150-003 — Tag releases bypass lint, security, and device/emulator gates

**Area:** release engineering
**Severity:** P1

#### Evidence

- `.github/workflows/ci.yml:3-9` ignores all tag pushes.
- `.github/workflows/ui-testing.yml:3-9` runs on pull requests, schedule, or manual dispatch, not tags.
- `.github/workflows/release.yml:11-45` allows publication after `runPureTests` and `runMockTests` only.
- Release does not run `lint`, the curated instrumented tests, the TalkBack test, the web-demo parity tests, or the Trivy scan.
- The regular Trivy job is itself `continue-on-error: true` (`ci.yml:105-115`).

A maintainer can tag a commit that was never on `main`, or tag before branch jobs finish, and still publish signed APKs. This matters more after v1.5 because backup encryption, private-copy entry points, CTC assets, custom-drawn accessibility, and API-21 behavior all depend on Android/runtime coverage that JVM tests cannot fully provide.

#### Required TODOs

- [ ] Refactor lint and curated instrumented checks into reusable workflows and call them from both PR/main CI and `release.yml`.
- [ ] Make the release job depend on `lintDebug`, `compileDebugAndroidTestKotlin`, the curated emulator gate, and the TalkBack test.
- [ ] Require the tagged commit to be reachable from the protected `main` branch.
- [ ] Require successful CI checks for the exact tagged SHA before signing/upload.
- [ ] Decide whether dependency/security scan findings block release; if not, document the accepted threshold rather than using an unconditional `continue-on-error`.
- [ ] Add web-demo parity/smoke tests to the deploy workflow and to release when release notes link to demo claims.

#### Acceptance test

A tag pointing to a commit with a lint error, failing instrumented test, or commit not on `main` must not create a GitHub release.

### CK-150-004 — v1.6 metadata has three incompatible descriptions of the shipping engine

**Area:** release correctness, user communication
**Severity:** P1

#### Evidence

- [ ] Run the existing release-preparation script/dry-run only after all blockers are resolved; then bump the SSoT version to 1.6.0 and verify tag/version/changelog codes.
- [ ] Add a drift test that checks the default engine and served-language set against release-note tokens, or generate this portion from `CtcLanguageSupport`/version metadata.

#### Acceptance test

The build version, tag, release body, F-Droid changelog, README, and runtime support table must agree on default engine, supported languages, provisional languages, and fallback behavior.

### CK-150-005 — Default CTC has no main-dictionary fuzzy rescue

**Area:** core typing correctness
**Severity:** P1

#### Evidence

- The removed neural path contained a model-independent main-dictionary fuzzy rescue.
- No equivalent consumer exists in `CtcEngineAdapter`; source search finds only comments describing the removed stage.
- The live priority file records the gap at `memory/todo.md:20-24` and `:238-241`.
- The visible fuzzy controls were removed/deprecated, confirming neither surviving engine exposes the behavior.

For a sufficiently poor trace, CTC can return a poor constrained-beam result or no usable result where the former decoder attempted a dictionary rescue. Since CTC is now the default and the neural fallback was removed, this is a direct behavioral regression from v1.5.

#### Required TODOs

- [ ] Port the model-independent rescue behind `CtcEngineAdapter`, using the merged active lexicon and a bounded candidate budget.
- [ ] Specify when rescue is permitted (empty slate, low confidence, or poor path fit) so it cannot override a confident CTC decode.
- [ ] Preserve privacy/logging gates and cancellation/stale-input behavior.
- [ ] Add real-trace A/B coverage for empty/low-confidence swipes and a latency ceiling.
- [ ] If intentionally deferred, call it out as a known v1.6 regression in release notes and provide an issue link.

#### Acceptance test

A fixed corpus of sloppy traces that previously required rescue must recover candidates without regressing the held-out CTC top-1/top-3 bar or exceeding the agreed p95 latency budget.

### CK-150-006 — CTC swipe decoding silently ignores the configured secondary language

**Area:** multilingual typing correctness
**Severity:** P1

#### Evidence

- `InputCoordinator.performCtcSwipeTyping` reads exactly one active language at `InputCoordinator.kt:690-705`.
- It calls `CtcEngineAdapter.decodeAsync(..., language)` once at `:739-740`.
- No secondary-language input is present in the CTC package or dispatch call.
- The project’s current task log records the resulting failure mode at `memory/todo.md:25-26` and `:242-244`: a French-primary/English-secondary user cannot receive English swipe results.

Tap typing supports configured language slots, so the swipe path violates the UI’s multi-language expectation without warning. This is especially visible after making CTC the default.

#### Required TODOs

- [ ] Define the product rule: dual-trie decode, two bounded decodes plus calibrated rank merge, or explicit single-language swipe behavior in the UI.
- [ ] Do not compare raw scores from CTC and geometric engines; merge only comparable same-engine results or define a rank calibration with evidence.
- [ ] Include primary/secondary language and generation in cache keys and cancellation guards.
- [ ] Add instrumented cases for primary-only, secondary-only word, rapid language swap, unsupported secondary fallback, and privacy/language-store isolation.
- [ ] Until fixed, show a setting description/warning that secondary language affects tap predictions but not CTC swipes.

#### Acceptance test

With French primary and English secondary, a held-out English swipe must produce the expected English candidate without leaking English contraction rules into French-only mode.

### CK-150-007 — CTC makes `ß`, `œ`, `æ`, and `ø` words unreachable

**Area:** multilingual typing correctness
**Severity:** P1

#### Evidence

- The shipping CTC model/trie is an `a-z` surface.
- `CtcAzProjection` deliberately drops CKDT words that have no `a-z` projection; the behavior is pinned by `CtcCkdtLexiconTest` and documented in `docs/specs/ctc-swipe-engine.md:355` and `:524`.
- `memory/todo.md:234-237` identifies examples including `groß`, `Straße`, and `weiß` while German is a CTC-served language.
- Geometric supports layout aliases, but selecting the default CTC path prevents these words from reaching it on otherwise supported Latin layouts.

This is not a theoretical arbitrary-alphabet limitation. It affects common words in an explicitly supported default language.

#### Required TODOs

- [ ] Choose and document an input projection for each unsupported grapheme (`ß`, `œ`, `æ`, `ø`) that matches how users trace the actual layout.
- [ ] If using aliases such as `ß -> ss`, re-run the per-language lambda/accuracy campaign because lexicon collisions and frequency retention change.
- [ ] Preserve canonical display forms and deterministic collision resolution.
- [ ] Add real German/French/Danish/Norwegian word fixtures and live-layout trace tests.
- [ ] Until fixed, route affected layouts/languages to geometric or disclose the limitation in the engine selector and release notes.

#### Acceptance test

Representative words containing each supported layout grapheme must be reachable from a real layout trace and returned in canonical display form, with no regression to the existing `fr/de/es` test bars.

## P2 findings — important follow-up

### CK-150-008 — TalkBack hit regions do not match the keyboard tap regions

`KeyboardGeometry.keyAt` assigns shifted-key gaps to the following key, extends the QWERTY `a` row into the left margin, and assigns right-of-row slop to the last key (`KeyboardGeometry.kt:62-135`). `computeKeyRects` creates only `[xLeft, xRight)` rectangles (`:161-209`). `KeyboardAccessibilityHelper.getVirtualViewAt` scans only those rectangles (`KeyboardAccessibilityHelper.kt:61-70`). Therefore TalkBack exploration has dead strips where normal taps still activate a key, despite comments claiming identical geometry.

TODOs:

- [ ] Produce non-overlapping virtual bounds from the same ownership partition used by `keyAt`, including shifted gaps and edge slop.
- [ ] Decide a finite host-view edge for right/left slop instead of unbounded rectangles.
- [ ] Add boundary tests for every gap, left margin, right margin, row shifts, placeholders, and RTL layouts.
- [ ] Add an instrumented hover test with touch exploration actually enabled.

### CK-150-009 — Context rescoring remains unsuitable for default CTC

The setting is safely default-off. The prior committed replay found CTC `3 fixes / 24 breaks` by case and `3 / 1` by distinct trace, failing the `<0.20` break/fix bar. The uncommitted harness improves fidelity, corrects phantom trace buckets and denominators, exposes `W/R_MIN`, and adds a trace-separated tune/confirm sweep.

The audit ran the changed harness on the device corpus with `replayMaxCtx=1`:

- CTC shipped point: **0 fixes / 0 breaks**; no benefit.
- CTC sweep selected `W=1.00 R_MIN=0.50` on tune with 2 fixes/0 breaks, then produced **0 fixes/0 breaks on confirm** and explicitly `meetsBar=false`.
- Geometric showed benefit, but geometric is secondary and cannot justify enabling the feature for default CTC.

TODOs:

- [ ] Keep `swipe_context_rescoring` default off.
- [ ] Do not present a zero-error/no-fix operating point as passing; retain the positive-benefit requirement.
- [ ] Gather on-device shadow-mode exposure rates and more independent CTC traces.
- [ ] Add contraction alias injection to `CtcReplayEngine` or bound its effect with a test.
- [ ] Commit a new evaluation report only after the current uncommitted harness changes are reviewed and reproducibly rerun.

### CK-150-010 — Thirteen new user-facing strings fall back to English in all 21 locales

The delta adds 460 default string names. Each locale contains 435 of them; 12 are intentionally non-translatable glyph/debug strings, while these 13 user-facing strings are absent everywhere else:

TODOs:

- [ ] Translate all 13 strings for all supported locales.
- [ ] Convert shortcut/step quantity copy to `<plurals>` where grammar varies.
- [ ] Remove the suppressions after coverage lands and add the names to the translation coverage test.

### CK-150-011 — Passphrase storage silently degrades to reversible base64

`BackupPassphraseStore` stores the backup passphrase as plain base64 on API 21/22 and after **any** API 23+ Keystore/provider exception (`BackupPassphraseStore.kt:117-140`, `:165-180`). The only signal is a log entry. The fallback is app-private and excluded from Android backup, so this is not equivalent to public plaintext; however, it removes the advertised Keystore defense-in-depth without telling the user and can occur on a supported device after an unexpected provider error.

TODOs:

- [ ] Expose storage protection state to the UI and headless status output.
- [ ] Distinguish expected API 21/22 fallback from unexpected API 23+ Keystore failure.
- [ ] Prefer fail-closed/no persistent headless passphrase on unexpected modern-device errors, or require explicit user acceptance of degraded storage.
- [ ] Add API 23+ Keystore round-trip/lost-key tests on device; the current MockK test covers only the fallback branch.

### CK-150-012 — Embedded NUL characters hide Kotlin changes from Git review

Actual `0x00` bytes occur in:

- `src/main/kotlin/tribixbite/cleverkeys/BackupRestoreManager.kt`
- `src/main/kotlin/tribixbite/cleverkeys/backup/crypto/BackupPassphraseStore.kt`

They represent char zeroing, but should be source escapes. Git treats `BackupRestoreManager.kt` as binary (`Bin 67107 -> 102553 bytes`), so ordinary diffs, blame review, search tools, and some scanners cannot inspect a security-critical 100 KB source file.

TODOs:

- [ ] Replace literal NUL bytes with the Kotlin source escape `'\u0000'`.
- [ ] Add a source-hygiene test rejecting NUL bytes in text extensions.
- [ ] Re-review the now-textual backup diff after conversion.

## Audit conclusion

The delta is not a failed rewrite. The core direction—CTC default plus geometric coverage, one swipe result pipeline, local learned context, strict backup allowlists, and custom-view accessibility—is coherent and substantially better tested than v1.5. The remaining blockers cluster at boundaries: untrusted archive application, multilingual parity, accessibility verification, and release truthfulness. Closing those boundaries should be the release criterion; adding more feature work should not be.
